# 完整演练：一张工资表，从 0 到 5

场景：用户在会话里丢来一句

> "帮我看看这个 6 月工资表，算得对不对？顺便看看钱都花哪儿了。"

附件是 `2026年6月员工薪酬明细表.xlsx`（10 人、14 列、4 行表头）。
下面是把它做完的全过程——**命令、产出、以及每一步该怎么想**。
文中的数字是这张示例表的真实结果，不是编的。

## Step 1：转结构化 MD

```
python3 <resources_path>/scripts/excel_ai.py tomd ~/OpenWorker/s-42/2026年6月员工薪酬明细表.xlsx -o ./01_raw_md
```

```
[tomd] 2026年6月员工薪酬明细表.xlsx / 工资明细表 → ./01_raw_md/2026年6月员工薪酬明细表/工资明细表.md
[tomd] 索引 → ./01_raw_md/00-索引.md
[tomd] 完成：1 个 Sheet
```

打开 MD，**四件事**：

**① 数据体从第几行开始**

```
- 推断表头行数：**4**（数据体从 Excel 第 **5** 行开始）
- 合并单元格：6 处（表头区 6 处 / 数据区 0 处）
> 写 spec.json 时：`"header_rows": 4`。表头行数数错一行全废，请先自己确认一眼。
```

表头区解析证实了它：第 1 行是跨 14 列的大标题（脚本已跳过），第 2 行是分组表头
（基本信息 / 固定项 / 浮动项 / 扣款项 / 其他增减 / 结果），第 3 行才是字段名，第 4 行是单位"元"。
**四行，对得上。**

**② 哪些是输入，哪些是结果**

列字段定义表里最后一列露了马脚：

```
| 13 | N | 结果 / 应发工资G / 元（公式勿动） | 15990.5 / 11630.75 / 20160 | 100% | 数值 |  |
```

"公式勿动"——这是**结果列**，只能当 `target`，绝不能进 `expr`。
另外列名里带着字母编号（基本工资A、岗位津贴A2、绩效工资B1、社保C1、补贴D、奖金E、罚款F、应发工资G），
这是典型的"公式写在列名里"：A/B/C/D/E/F 是加减项，G 是结果。

**③ 校验列**：本表没有 check 列（有的话优先拿来做锚点）。

**④ 类型告警**：「六、告警与注意事项」是"无"，说明没有混合类型列、公式列也不是全空。
（如果这里写「有公式但取值全空」，先停下——见 `pitfalls.md` 第 11 条。）

**「三、真实公式清单」是空的**：这张表的公式已经被转成静态值了。
所以**公式只能从列名和数值反推**，Step 4 的验证就更不能省。

## Step 2：字段本体（写进 `02_ontology/字段本体.md`）

按业务域组织，不按列顺序平铺：

| 域 | 字段 | 业务含义 | 类型 | 角色 | 计算关系 |
|---|---|---|---|---|---|
| 主数据 | 工号 | 全公司唯一标识 | 文本 | 人工输入 | — |
| 主数据 | 姓名 / 一级部门 | 人员与归属 | 文本 | 系统带出 | — |
| 固定项 | 基本工资A | 月度固定薪 | 金额 | 系统带出（调薪表） | 输入 |
| 固定项 | 岗位津贴A2 / 工龄工资A3 | 岗位与司龄补贴 | 金额 | 系统带出 | 输入 |
| 浮动项 | 绩效工资B1 | 绩效系数 × 绩效基数 | 金额 | 中间计算（源表未提供） | **待确认** |
| 浮动项 | 加班费B2 | 加班工时折算 | 金额 | 系统带出 | 输入 |
| 扣款项 | 社保C1 / 公积金C2 | 个人承担部分 | 金额 | 系统带出 | 输入（扣减） |
| 其他增减 | 补贴D / 奖金E | 增项 | 金额 | 人工输入 | 输入 |
| 其他增减 | 罚款F | 减项 | 金额 | 人工输入 | 输入（扣减） |
| 结果 | 应发工资G | 本月应发合计 | 金额 | **最终输出（公式勿动）** | 见 Step 3 |

**取值陷阱**：本表金额列填充率 100%、无 `/` 与 `-` 占位符；`罚款F` 的 0 是"本月无罚款"，是真 0。

**待确认问题**：
1. 绩效工资 B1 的源表（绩效系数 × 基数）本次未提供，无法做跨表验证；
2. 应发 G 之后是否还有个税、实发口径？本表未体现。

## Step 3：公式链与血缘（写进 `02_ontology/公式链与血缘.md`）

**分层公式链**——从列名与数值反推，Step 4 会验证它对不对：

```
第一层 输入      A=基本工资  A2=岗位津贴  A3=工龄工资  B2=加班费
                 C1=社保     C2=公积金    D=补贴  E=奖金  F=罚款
第二层 中间量    AA = A + A2 + A3        （固定项小计）
                 BB = B1 + B2            （浮动项小计）
                 CC = C1 + C2            （扣款小计）
第三层 结果      G  = AA + BB - CC + D + E - F
                    = A + A2 + A3 + B1 + B2 - C1 - C2 + D + E - F
```

**跨表血缘**：

| 源 | 目标 | 连接键 | 说明 |
|---|---|---|---|
| 绩效表.绩效系数（本次未提供） | 工资明细表.B1 绩效工资 | 工号 | 系数 × 绩效基数，**待确认** |

**可扰动的输入点 → 影响层级**（Step 5 的 What-If 照着做）：

| 输入点 | 影响 |
|---|---|
| A 基本工资 | → AA → G（全员，杠杆最大） |
| B1 绩效工资 | → BB → G（与绩效系数联动） |
| C1/C2 社保公积金 | → CC → G（政策基数调整时批量变） |

## Step 4：验证（核心）

写 `spec.json`——用 `write_file` 写成文件，**不要 heredoc**。

```json
{
  "workbook": "/Users/you/OpenWorker/s-42/2026年6月员工薪酬明细表.xlsx",
  "sheet": "工资明细表",
  "header_rows": 4,
  "keys":       {"ID": "工号", "NAME": "姓名"},
  "dimensions": {"DEPT": "一级部门"},
  "fields": {
    "A": "基本工资A", "A2": "岗位津贴A2", "A3": "工龄工资A3",
    "B1": "绩效工资B1", "B2": "加班费B2",
    "C1": "社保C1", "C2": "公积金C2",
    "D": "补贴D", "E": "奖金E", "F": "罚款F",
    "G_x": "应发工资G"
  },
  "derived": {
    "AA": "round(A+A2+A3, 2)",
    "BB": "round(B1+B2, 2)",
    "CC": "round(C1+C2, 2)"
  },
  "checks": [
    {"name": "应发工资G", "target": "G_x",
     "expr": "round(A+A2+A3+B1+B2-C1-C2+D+E-F, 2)", "tolerance": 0.01}
  ],
  "skip_when": {"empty": ["ID"], "label_in": ["汇总", "合计", "总计", "小计"]}
}
```

注意两个细节：

- 结果列变量叫 `G_x`（Excel 现值），公式链里的 `G` 是你的理解——**两者对撞才叫验证**。
- `expr` 直接展开到输入层，没有写成 `AA+BB-CC+D+E-F`。这样某一层错了不会连锁污染。

```
python3 <resources_path>/scripts/excel_ai.py verify spec.json -o ./03_verify
```

```
[verify] 数据行 10，校验项 1，比对 10 次，不匹配 2 次，通过率 80.00%
         - 应发工资G   比对 10  不匹配 2  通过率 80.00%  最大差 100.0000
[verify] 报告 → ./03_verify/验证报告.md
[verify] 注意：有不匹配时先别假设是自己错——也可能是这张 Excel 本身算错了。
```

### 读结果（这一步决定这次分析值不值钱）

报告的「四、不匹配明细」：

| Excel行号 | ID | NAME | DEPT | 校验项 | AI值 | Excel值 | 差异 |
|---|---|---|---|---|---|---|---|
| 7 | E003 | 赵敏 | 研发中心 | 应发工资G | 20060 | 20160 | **-100** |
| 13 | E009 | 刘洋 | 财务部 | 应发工资G | 10220 | 10220.05 | **-0.05** |

报告还补了一句：`另有 1 次差异非零但在容差内（浮点尾差），不计为不匹配。`（那是 E007，差 0.005。）

**差异模式速查**给出的判读是：`只有零星 2 行差（20.0%）→ 多半是人为覆盖或错误`。

**先别假设是自己错。** 逐条判：

- **8/10 行严丝合缝**（含 E001 的 15,990.50、E010 的 51,260.00 这种多位小数）→
  公式链 `G = A+A2+A3+B1+B2-C1-C2+D+E-F` **是对的**。如果是我理解错了，
  错的不会只有 2 行，而是全表按同一模式偏。
- **E003 赵敏 +100.00**：整百、只此一行 → 典型的**人为覆盖**。要么是漏记的一笔补发，
  要么是手滑改了结果列（这列写着"公式勿动"）。**这是本次分析最有价值的发现。**
- **E009 刘洋 +0.05**：不是整数、超出 0.01 容差 → 更像结果列被手工微调过，或某一项的
  舍入口径与其他人不同。金额不大，但同样属于"结果列和输入对不上"。
- **E007 郑爽 +0.005**：在容差内，属于浮点尾差，正常。

**绝对不能做的事**：把 `tolerance` 从 `0.01` 放大到 `0.1` 或 `101`，让报告变成 100%。
那等于把 Excel 里唯一的两处真问题亲手抹掉——用户请你来就是为了这两行。

**要做的事**：把这两行单列出来交给用户核，并明确写清结论：

> 10 名员工 × 1 项公式，通过率 80%。公式已还原并验证：
> 应发工资G = 基本工资A + 岗位津贴A2 + 工龄工资A3 + 绩效工资B1 + 加班费B2 − 社保C1 − 公积金C2 + 补贴D + 奖金E − 罚款F。
> 8 人完全一致。**2 人的"应发工资G"与各项明细对不上，判断是表里的值被人为改过，不是公式理解有误**：
> - E003 赵敏，表里比明细合计多 **100.00 元**（20,160.00 vs 20,060.00）
> - E009 刘洋，表里比明细合计多 **0.05 元**（10,220.05 vs 10,220.00）
> 这两行请业务确认：是漏记的补发，还是误改了标着"公式勿动"的结果列？

（如果通过率是 0% 或全表差一个固定值，那多半是你错了：回 Step 3 找漏掉的项、
或回 Step 1 确认 `header_rows`。）

分析报告的骨架（真实输出节选）：

```
## 1、分组汇总
| DEPT | 人数 | 占比 | G_x 总额 | G_x 人均 | G_x 占比 |
| 研发中心 | 4 | 40.00% | 99,041.25 | 24,760.31 | 57.53% |
| 财务部   | 3 | 30.00% | 41,040.46 | 13,680.15 | 23.84% |
| 市场部   | 3 | 30.00% | 32,081.00 | 10,693.67 | 18.63% |
| **合计** | 10 | 100.00% | **172,162.71** | 17,216.27 | 100.00% |

## 4、离群检测（IQR，k=1.5 → 正常区间 [-118.38, 28,391.23]）
| 1 | 高峰 | E010 | 研发中心 | 51,260.00 | 偏离 22,868.77 |

## 6、What-If：基本工资普调 5%（重算中间量 AA）
| 应发G | 现状合计 172,062.65 | 情景合计 178,869.65 | 变化 +6,807.00 | 变化率 3.96% |
```

**脚本给的是骨架，洞察要你自己写**，附在报告末尾或回复里：

> - **钱花在哪**：月度应发合计 17.2 万，研发中心 4 人占 57.5%（人均 2.48 万，是市场部人均的 2.3 倍）；
>   高峰一人就占全公司 29.8%，是 IQR 口径下的唯一离群点——不是异常，是薪酬结构本身高度集中。
> - **要人去核的**：E003（+100.00）、E009（+0.05）两处结果列与明细对不上，见上。
> - **杠杆**：基本工资普调 5% ⇒ 月成本 +6,807 元（+3.96%），年化约 8.2 万；
>   由于 A 占应发的比重最大，它是所有输入点里杠杆最高的一个——若要控总额，先谈 A 的调幅。

## 这次演练用到的纪律，回顾一遍

1. `header_rows` 亲自数了一遍，没有直接用推断值
2. 标着"公式勿动"的 `应发工资G` 只做 `target`，没有进 `expr`
3. `expr` 展开到输入层，没有引用中间量结果列
4. 通过率 80% 时**没有放大容差**，而是把 2 行差异当成发现交出去
5. 结论里写清了"多少条 × 多少项、通过率多少、不匹配的是谁的错"
6. 原表全程只读，产物全在独立输出目录
7. `spec.json` 交给了用户，并讲了它的复用方式
