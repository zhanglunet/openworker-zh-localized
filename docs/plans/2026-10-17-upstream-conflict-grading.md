## 1. 冲突三级

打个比方：上游变更像寄来的一箱新零件。文本冲突是"零件上的标签换了 wording"——
照着重贴中文标签就行；结构冲突是"零件的形状和安装孔位都变了"——得先看新图纸；
功能删除是"厂家说这个零件停产了"——得决定是自己造、找替代，还是跟着停。

| 级别 | 名字 | 判定信号（看什么） | 处理原则（保留哪边、谁拍板） |
|---|---|---|---|
| 一级 | 文本冲突 | compare 显示 `modified`/`removed` 且命中 `surfaces/gui/src/`（即 T3 报告的 P0）；或 `sync-upstream.yml` 的同步 PR 里 tsx/ts 文件出现 `<<<<<<<` 冲突标记，但冲突块只是字符串字面量 | 内容保留汉化版（中文），结构接受上游。做法：取上游的新代码结构，把中文字符串按新位置填回去。拍板：汉化维护者直接定，不用开会 |
| 二级 | 结构冲突 | compare 显示 `renamed`，或文件在目录间移动，或单文件 `additions+deletions` 很大（组件重构）；git 三方合并对"重命名 + 内容修改"的组合最脆弱，极易误判 | 先跟上游的结构走（新路径、新组件划分），再把汉化内容搬运过去，不在旧结构上硬留。禁止：为了省事在上游文件里大段重写（下次同步会再冲突一次）。拍板：汉化维护者；拿不准的开 issue 讨论，不猜 |
| 三级 | 功能删除 | compare 显示 `removed`，且被删的东西是汉化版独有内容（`website/`、中文文档、汉化版自己加的逻辑）所依赖的；或上游删掉了一个用户在用的功能 | 三选一：① 自己维护（fork 该功能进汉化版，承担后续同步成本）；② 跟随删除（同步删中文相关代码和文档）；③ 找替代（上游推荐的新方案）。拍板：这是产品决策，维护者给建议、由负责人（john）拍板，结论写进 issue |

分级是"就高不就低"：一次同步里同时出现文本和结构冲突，按二级走；
出现功能删除，直接按三级走。

## 2. 处理流程：从 T3 报告到合入

```
T2 检测 (JSON) → T3 报告 (P0/P1/P2) → 本稿分级 (一/二/三级)
    → 开 issue（P0 当天，标题格式见 T2 §3.2；正文贴报告 + 分级结论）
    → 本地处理（按下表）→ 同步 PR（merge commit，禁止 squash）
    → 合入 main → 推进基线书签（--update-state）
```

分级与动作对照：

| 分级 | issue 动作 | 处理动作 |
|---|---|---|
| 一级（文本） | P0 issue 当天开，正文加一行"分级：一级·文本冲突，预计 X 文件重翻" | 按 T3 报告 §4.3 的 P0 清单逐文件重翻，本地验证后合入 |
| 二级（结构） | issue 里列出重命名/移动前后路径对照表 | 先合上游结构，再搬运汉化内容；合入前 diff 逐文件过一遍，确认没有中文字符串被结构变更"吞掉" |
| 三级（功能删除） | issue 里写清三选一的建议与成本，@负责人拍板 | 按拍板结论执行；选①的要在 issue 里注明"后续同步持续成本" |

两种 issue 别混（T2 §3.2 已定，本稿重申）：

- 《上游同步需要人工解决冲突》——`sync-upstream.yml` 自动开的，意思是"代码合并不上"，
  走本稿 §1 分级处理的是"合上之后"的事；
- 《上游同步 YYYY-MM / YYYY-MM-DD》——T2 检测开的，意思是"中文要重翻"，
  正文必须引用本稿的分级结论（一级/二级/三级 + 处理动作）。

## 3. 回退流程：以汉化版 tag 为锚点

回退分三种时机，越往后成本越高：

**时机 A：同步 PR 还没合入 main。**
直接在 `sync/upstream-main` 分支上修；修不好就关掉 PR 重开一个。
基线书签（`docs/upstream/sync-state.json`）还没动，不用回退。

**时机 B：已合入 main，但还没打 tag 发布。**
公开仓禁止 `git reset --hard` + force-push main。用 revert：

```bash
git revert -m 1 <同步的 merge commit sha>   # -m 1 表示保留 main 这边
```

revert 本身走正常 PR 合入。基线书签若已用 `--update-state` 推进，
把 `last_synced_tag` / `last_synced_sha` 回指到 revert 后的位置，
并在 commit message 注明原因，避免"书签已过、代码已回"的不一致。

**时机 C：tag 已打出去了。**
tag 一旦发布就不删除（客户端可能已缓存）。做法：revert 后发一个新版本；
同时把 `releases/latest-zh.json` 的下载地址回指上一稳定版
（与 PRD-030 第 3 章 §2.5 的回滚同理：回滚不重新构建，回指即完成）。

回退后的复盘：无论哪个时机，回退原因记一条到当月的同步 issue；
建议在下次试运行时演练一次时机 B，检查回退流程是否走得通。

## 4. 真实案例：汉化仓 PR #2 的 squash 教训（流程反例）

- 事实（2026-10-17 已核实）：PR #2《sync: merge upstream OpenWorker 01b6f83》
  已合并，但它的合并提交只有一个 parent——确为 squash 合并。
- 后果：squash 把合并结果压成单亲提交，被同步方的 tip 从此不再是本仓祖先；
  下一次同步时，git 找不到共同祖先，已解决过的冲突被**全部重放**（约 20 个文件）。
- 定级：这不是内容冲突，是**流程级反例**——它说明"分级处理得再好，
  合入方式错了等于白干"。
- 规则（已在 PRD-030 第 2 章 §3.1 落实，本稿重申）：同步 PR 必须用 merge commit
  合并，禁止 squash / rebase 合并；仓库设置里对 `sync/*` 分支的 PR 仅允许
  merge commit。

## 5. 与 T3 报告的衔接点（给执行人的检查项）

1. 拿到 T3 报告先看 §4.3 的 P0/P1/P2，再按本稿 §1 定级（一/二/三级）。
2. 开 P0 issue 时，正文除贴报告全文外，加一行分级结论
   （例："分级：二级·结构冲突，3 个文件重命名，见下表"）。
3. 合入前对照：merge commit（`git log --merges -1` 能看到两个 parent），
   不是 squash。
