# openworker-zh-localized 上游同步策略（T1 设计稿）

> PRD-029/T1（trend #175）。本稿为可直接执行的策略文档，T2–T4 在此基础上细化。

## 1. 同步频率

| 档位 | 周期 | 触发条件 |
|---|---|---|
| 基准 | 每月一次（每月 5 日前出上月报告） | 默认 |
| 加密 | 每双周一次 | 上游两周内 release ≥ 2 个，或单次 release 说明中出现 breaking change 字样 |

beta 期（上游 README 自述 open beta）默认走加密档；上游宣布 GA 后降回基准档。

## 2. 监控对象（两层）

| 层 | 仓库 | 作用 | 监控内容 |
|---|---|---|---|
| L1 源头 | `andrewyng/openworker` | 功能真相 | main 分支 tag/release、大版本说明 |
| L2 中转 | `Lenovo202409/openworker-zh` | 汉化版直接基线 | main 分支 commit（汉化版基于它二次整理） |

只看 L2 会漏掉"中转层还没跟上游"的窗口期；只看 L1 会把"中转层已处理"的变更重复算。报告里两层分开列。

## 3. 检测方式

- GitHub API：`GET /repos/{owner}/{repo}/releases` 取 tag 列表；`GET /repos/{owner}/{repo}/compare/{base}...{head}` 取文件级 diff。
- 基线锚点：每次同步后记录 `last_synced_tag`（L1）与 `last_synced_sha`（L2），下次从锚点往后比。
- 汉化敏感区清单（命中即标红）：
  - UI 字符串文件（`*.json` / `locales/` / `i18n/` 下，以实际仓库结构为准，T2 落实时核对）
  - 文档（`docs/`、`website/` 文案）
  - 官网中文站文案（oaosf.cn 对应源码目录）

## 4. 汉化 diff 报告格式

每份报告固定四节：

### 4.1 变更摘要矩阵

| 变更类型＼影响面 | 影响已汉化文件 | 未影响已汉化文件 |
|---|---|---|
| 新增 | ⚠️ 需汉化（列文件清单） | 记录即可 |
| 修改 | ⚠️ 需重翻（列文件清单） | 记录即可 |
| 删除 | ⚠️ 跟随删除僵尸翻译 | 记录即可 |

### 4.2 工作量估算

- 新增字符串数（从 diff 中抽取新增 key/文案行数）
- 需重翻段落数（修改类变更中落在敏感区的）
- 估算单位：按"每 50 字符串 ≈ 0.5 人日"粗估，T5 试运行后校准系数。

### 4.3 优先级建议

- P0：影响已汉化 UI 字符串的修改/删除（用户看得见）
- P1：新增功能的字符串（功能可用但显示英文）
- P2：文档类变更

### 4.4 两层对照

L1 与 L2 的变更分开两节列，末尾给一句话结论（如"L2 已同步 L1 vX.Y.Z，本轮只需处理 L2 增量"）。

## 5. 告警与归档

- 检测到 P0 变更：当天在 trend 仓库开一条同步 issue（标题格式 `上游同步 YYYY-MM：<一句话摘要>`），正文贴报告。
- 无 P0 变更：报告归档到 `docs/updates/`（与现有更新日志机制衔接），不打扰。
- 每份报告保留 `last_synced_tag`/`last_synced_sha`，作为下次基线。

## 6. 与 PRD-020 的关系

本策略的"只读镜像 + 定期同步"框架复用 PRD-020（deepseek-harness fork 同步策略）；
差异点：汉化版多了"语言层 diff"维度（上游的功能变更 vs 汉化工作量是两回事），
这是本策略独有的第 4 节。
