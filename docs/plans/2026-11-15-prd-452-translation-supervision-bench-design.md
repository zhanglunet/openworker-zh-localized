# 翻译监督台设计草稿（PRD-452/T1）

> 状态：设计草稿（T1），仅供评审，未实现
> 来源：[trend #2180](https://github.com/zhanglunet/trend/issues/2180)（[PRD-452/T1] 翻译监督台设计）；
> PRD 全文：`zhanglunet/trend` 仓库 `adopted/PRD-452-owzh-translation-supervision-bench.md`
> 目标仓：[zhanglunet/openworker-zh-localized](https://github.com/zhanglunet/openworker-zh-localized)
> 落点：`docs/plans/2026-11-15-prd-452-translation-supervision-bench-design.md`

## 1. 问题与目标

翻译 agent 出稿时，人工没有一个地方能全程看到一段译稿是怎么产生的：选了什么术语、按什么顺序出稿、中间改过几版。
问题往往拖到人工拍板那一刻才被发现——那时再发回重译，成本最高。

翻译监督台补这一环：每段译稿出稿时都经过监督台，人可以

- 看到译稿的出炉过程（原文段、术语选择、出稿版本）；
- 随手批注、裁决；
- 一键把反馈发回 agent，agent 改完再回来。

目标是：问题译稿在出稿时就被批注发回重译，人工拍板时只审已经被人点头过的译稿。

## 2. 范围与非目标

范围：翻译 agent 出稿全程的人审监督——看、批注、裁决、发回、再回来。

非目标（不属于本监督台，另有 PRD 负责）：

- 不验证译稿本身的对错（评审流水线 PRD-429 的事）；
- 不产生新译稿（监督台只监督，不写作）；
- 不管待办清单与收件箱管理（收件箱 PRD-369 的事）；
- 不做 checklist 失败验证（PRD-383 的事）。

## 3. 数据模型：三件套落账

监督台只存三类记录，全部落账、可追溯：

### 3.1 进度（Progress）

一段译稿的一次出稿过程是一条进度记录：

- 译稿标识：原文段编号 + 译稿版本号（每次 agent 改完回来，版本号 +1）；
- 出稿步骤：原文段、术语选择、译文初稿、修订版（如有）；
- 状态：`出稿中 / 待人审 / 已点头 / 已发回 / 已关闭`；
- 时间戳：每步的开始与结束时间。

### 3.2 批注（Annotation）

人对译稿的每一条意见都是一条批注记录：

- 锚点：批注挂在哪个位置（原文段编号、译文行号或术语词条）；
- 内容：意见正文；
- 类型：`换术语 / 重译 / 疑问 / 通过`；
- 作者与时间；状态：`待处理 / 已采纳 / 已驳回`。

### 3.3 发回反馈（Feedback）

一次"发回 agent 改"的动作是一条反馈记录：

- 关联的批注列表（一次发回可带多条批注）；
- 发回指令：要求 agent 做什么（换术语 / 重译整段 / 只改指定处）；
- 发回时间、agent 回来后的新版本号；
- 闭环：agent 回来后，旧批注逐条标记为"已处理 / 未处理"，未处理的继续挂在新版本上。

三件套之间用译稿版本号串联：同一原文段的不同版本共享一条进度链，批注与反馈都挂在具体版本上，版本变了，旧批注不丢失。

## 4. 监督接入点与批注方式

### 4.1 接入点

翻译 agent 出稿流程在三个点上向监督台"报到"：

1. **出稿开始**：agent 认领一段原文，监督台新建一条进度记录（状态"出稿中"）；
2. **出稿完成**：agent 交出译稿初版，进度记录转为"待人审"，人开始能看到它；
3. **改完回来**：agent 按反馈改完交回新版，进度记录回到"待人审"，版本号 +1，旧批注带到新版上对照。

接入点只做"报到 + 交稿"，不干预 agent 内部的翻译逻辑。

### 4.2 批注方式

- 人在译稿视图上直接点选一段译文或一个术语，写批注；
- 批注即时保存，不用等整段审完；
- 一条批注可以单独发回，也可以多条批注攒成一次反馈一起发回；
- 发回是一键动作：点"发回 agent"，选中的批注打包成一条反馈记录，agent 侧收到待办。

### 4.3 裁决

人对每段译稿只有两种裁决：

- **点头**：译稿通过，状态改为"已点头"，进入下游人工拍板收件箱；
- **发回**：译稿不通过，按 4.2 发回 agent 改。

没有"默认通过"：超时未裁决的译稿一直停在"待人审"，不自动流向下游。

## 5. "人点头才进下游"的关口

关口规则只有一条，写死在监督台层面：

> 未点头的译稿不进人工拍板收件箱。

- 收件箱只读取状态为"已点头"的译稿；
- "待人审""已发回""出稿中"的译稿在收件箱里不可见；
- 点头动作本身也是一条落账记录（谁、在什么时候、点了哪一段、哪个版本）。

## 6. 界面与交互（概念级）

监督台视图分三栏，不规定具体技术实现：

- 左栏：待审译稿队列（按"待人审"时间排序）；
- 中栏：当前译稿（原文段对照译文，术语高亮，版本切换）；
- 右栏：批注列表与发回面板（写批注、选批注、一键发回）。

交互原则：批注随手写、发回一键走、版本随时切、旧批注不丢。

## 7. 验收标准

1. 设计评审通过（本 T1 的验收标准）。
2. 数据模型能覆盖"进度 + 批注 + 发回反馈"三件套，且同一原文段多版本之间批注不丢失（T2/T5 验证）。
3. 三个接入点（出稿开始、出稿完成、改完回来）都有明确的报到与状态流转定义。
4. 关口可验证：未点头的译稿在人工拍板收件箱中不可见；超时未裁决不自动放行。
5. 文档与示例中不出现真实内部主机名、IP、账号或密钥，一律用占位符。

## 8. 红线

- 只借鉴形态，代码复用需署名；LoopForge 零代码零文本复用（见第 9 节）。
- 实现类 PR 只开不合并，等用户 review。
- 未点头的译稿不进人工拍板收件箱。
- 本仓既有红线继续生效。
