### 1.2 加载与检索机制现状（决定 T4 的事实）

- **技能加载**：`coworker/skills/store.py` 按技能 name 查找（项目 `.coworker/skills/<name>/SKILL.md` 优先于全局技能目录），`rows()` 列举时把 SKILL.md 的 description 作为"菜单条目"交给模型判断何时适用。**当前运行时没有独立的触发词匹配引擎**——技能命中靠 description 文本，这一点决定了登记册的定位（见 §5.1 的诚实边界）。
- **角色加载**：`coworker/personas/`（manifest / registry / loading）按 persona.md 解析安装；安装动线为本地目录安装（设置页选 `role-packs/<包>/`，核对中文授权摘要后启用），技能另行拷入技能目录或走 zip 上传（暂存 → 预览 → 确认）。
- **包结构硬约束**：包根目录只放 `persona.md` 一个 .md 文件，多放一个 .md 安装器就会解析失败。此约束直接决定登记册的存放位置（见 §5.5）。

## 5. 中文触发词登记册设计（本仓增量重点）

### 5.1 定位与诚实边界

登记册是**发行侧登记资产**：把散落在各 SKILL.md description 里的口语触发例句结构化登记，统一优先级与冲突标注，供 T4 的检索适配消费、供 T5 抽样验收比对。它**不是**声称运行时已有触发词匹配机制——当前运行时靠 description 菜单条目由模型判断（§1.2）。登记册与 description 的关系：登记册是单一事实源，description 例句应与登记册一致；两边不一致时以登记册为准修订 description（修订动作归 T3）。

### 5.2 登记册字段定义（T3 按此执行）

每条触发词一行登记，字段如下：

| 字段 | 必填 | 说明 |
|---|---|---|
| entry_id | 是 | 登记册内唯一编号，建议格式 `TRG-<包缩写>-<三位序号>`（如 TRG-SALES-001） |
| 触发词 | 是 | 口语原文，保留用户说法全貌（如「帮我写个 JD」），不用关键词截断代替原句 |
| 触发词类型 | 是 | 三类：`句式`（完整口语句，如「帮我整理一下这家客户」）/ `场景词`（点明职业场景或对象的词，如「合同」「面试」）/ `产物词`（点明目标产物的词，如「JD」「跟进邮件」） |
| 所属技能 | 是 | 技能 name（zh-hr-jd-draft 等），触发命中最终落到技能 |
| 所属包 | 是 | pack_id（sales / legal / hr） |
| 优先级 | 是 | P0–P3，按 §5.4 规则赋值，不靠感觉填 |
| 冲突标注 | 是 | `无` / `同包多技能` / `跨包`；非「无」时必填冲突对象与处理方式两列 |
| 冲突对象 | 条件必填 | 与本条构成冲突的 entry_id 列表 |
| 处理方式 | 条件必填 | `优先级裁决`（注明靠哪一级决出）/ `待澄清`（运行时应反问用户）/ `可共存`（注明理由） |
| 来源 | 是 | `description 抽取`（注明出自哪个 SKILL.md）/ `人工新增`（注明新增理由） |
| 状态 | 是 | `启用` / `停用`（停用须注明原因，不删行，保留留痕） |
| 备注 | 否 | 语境限定（如仅限某语境成立）、与 terms.txt 语境分叉的关联等 |

存放格式建议：Markdown 表格文档（人可读、可评审）为登记册正本，T3 落地时定稿；是否再派生机器可读格式（如 JSON）由 T4 按消费方式决定，本稿不预先造双份。

### 5.4 收录原则与优先级规则

收录原则：

1. **口语优先**：收用户真会说的整句（「帮我写个…」「帮我看看…」「帮我整理…」「帮我准备…」句式族），不收内部术语式说法（如「执行合同风险清单生成」）。
2. **可落点**：每条触发词必须能落到一个具体技能；落不到的先不收，记入登记册文末"待观察区"，不硬塞。
3. **过术语口径**：登记册文案遵循基表 25 条 + `role-packs/terms.txt` 追加表口径；触发词是用户原话摘录时保留原话，但登记册的说明文字不得用错译法。
4. **不收纯闲聊与越界请求**：命中包红线的说法（如「帮我把跟进邮件发出去」）不登记为触发词，可在对应技能备注里登记为"红线说法示例"供 T5 误命中验证用。

优先级规则（冲突裁决的依据，数值越小越优先）：

| 级别 | 含义 | 例 |
|---|---|---|
| P0 | 显式点名：句子点到技能产物名或角色名 | 「做一份合同风险清单」点到产物名 |
| P1 | 完整句式精确命中种子例句同族句式 | 「帮我写个 JD」 |
| P2 | 产物词命中 | 句中出现「JD」「跟进邮件」「面试题纲」等产物词 |
| P3 | 场景词命中 | 句中只有「合同」「面试」等场景词，无产物词 |

裁决顺序：先比级别（P0 > P1 > P2 > P3），同级再比所属包与当前会话角色是否一致（会话已选某角色时，同包优先）。仍无法裁决的，处理方式标 `待澄清`，不由登记册硬判。

### 5.5 存放位置

受 §1.2 包根硬约束，登记册**不得**放进任何 `role-packs/<包>/` 目录内。建议位置：`role-packs/registry.md`（role-packs 根目录，不在单包目录内，不影响安装器对单包的解析）。T3 落地时须实测验证该位置不影响三包安装动线，并把验证结果写进 T3 的 PR 描述。

### 5.6 盘点得出的真实冲突例（T3 必须逐条标注）

以下是盘点阶段已识别的冲突，不是假设，T3 登记时逐条给出冲突标注与处理方式：

| 冲突 | 涉及技能 | 说明与预判处理 |
|---|---|---|
| 「看看这份合同…」类说法 | zh-contract-risk-list × zh-legal-doc-checklist（同包多技能） | 同句可读作"看风险"也可读作"核对齐不齐"；靠产物词裁决（出现"风险/不利"走风险清单，出现"缺什么/带什么文件"走核对清单），无产物词时标 `待澄清` |
| 「帮我写个…」句式族 | zh-hr-jd-draft × zh-sales-followup-draft（跨包） | 句式相同、产物不同；靠产物词（JD / 跟进邮件）裁决，属 `可共存`（产物词可区分） |
| 「整理」动作词 | zh-sales-lead-brief（整理客户材料）× zh-hr-interview-guide（整理招聘环节清单在 persona 职责内，但其技能 description 未收此说法） | 动作词本身不定包，登记时「整理」只作场景词（P3）不单独成条，或成条时必须绑产物词 |
| 「帮我准备…」 | zh-hr-interview-guide「帮我准备面试问题」为已收种子；销售侧"准备客户材料"类说法暂未收 | T3 补收销售侧说法时须与本条互标冲突对象 |

## 6. 按包加载与检索适配要点（T4 的设计输入）

不断链约束（T4 动工前逐条核对，任一不满足即停）：

1. 技能 name 与角色 id 不改名、不改大小写（`store.py` 按 name 查找、persona 按 id 关联 skills 字段，改名即断链）。
2. `role-packs/` 目录路径与三包目录名不动（`role-packs/README.md` 安装动线、发行门脚本、`tests/test_role_packs.py` 均按此路径引用）。
3. 包根"只放 persona.md 一个 .md"的硬约束不破（登记册按 §5.5 放包外）。
4. persona frontmatter 字段不增删改名（PRD-183/T1 §3.2 字段表已拍板，分层信息不塞进 frontmatter，走登记册承载）。

检索路径设想（供 T4 设计，本稿只定方向不定实现）：

- 用户中文口语句 → 查触发词登记册（按 §5.4 优先级裁决）→ 得所属技能 name 与所属包 → 技能经现有 `store.py` 查找路径加载（项目目录优先、全局目录兜底），角色经现有 registry 按 id 加载。
- 登记册未命中时回落到现有行为（description 菜单条目由模型判断），不因登记册缺失而阻断使用。
- 登记册可作为 PRD-212（中文 skill 同步清单）的数据源之一：同步清单需要"有哪些中文技能、各自定位"时读包级登记与触发词登记册，避免再造一份清单。此为接口预留，212 的同步机制本身不在本 PRD 范围。
