## 3. 三类检查的规则细则

### 3.1 漏翻检查：上游有 → 中文必须有对应

**检查对象**：复用 PRD-029 的汉化敏感区（`surfaces/gui/src/`、`docs/`、`website/`；
排除 `docs/plans/`、`*test*` 文件——测试断言的英文不需要翻，PR #15 已落地）。

**方案 A 口径（启发式，默认）**：

1. 锚点是**文件路径对应**：上游 `surfaces/gui/src/X.tsx` ↔ 汉化版同路径文件。
   上游 compare 显示某文件新增/修改后，抽取其中新增的英文字符串字面量
   （引号包裹的纯 ASCII 文本，长度 ≥ 3）。
2. 在汉化版对应文件的 diff 位置附近（±20 行窗口）找中文字符：
   有中文覆盖 → 视为已翻；**英文原样残留**（与上游完全相同的英文字符串
   出现在 UI 文本位置）→ 记为"疑似漏翻"，列出文件、行号、上游原文。
3. 豁免（不算漏翻）：品牌专有名词（OpenWorker、GitHub、Slack……）、代码标识符、
   URL、纯数字/格式串（如 `%d`、`{count}` 只有占位符的）。

**方案 B 口径（key 精确对齐，备用）**：

1. 上游 `en.json` 的每个 key，在汉化版语言包中必须存在且值非空。
2. 值不能与 `en.json` 完全相同（英文原样 = 漏翻）。
3. 上游删除的 key，汉化版对应 key 30 天内清理（过期 key 告警，不算失败）。

### 3.2 术语一致性：同一英文术语，全仓库中文必须一致

**扫描范围**：`surfaces/gui/src/**/*.tsx|ts`（不含 `*test*`）+ `docs/` 中文文档。
后端 `coworker/` 暂不纳入——`ops.md` 还是英文，等汉化后纳入（T4 基线时复核）。

**规则**：

1. 以 §4 术语表为准。每个英文术语，在扫描范围内出现的所有**中文译法**必须唯一。
   同一文件出现两种以上译法 → 失败，指出文件、行号、两种译法。
2. 只查中文译法：代码/注释里的英文术语本身出现不算（那是源码，不是文案）。
3. 大小写/单复数归一：`Skill`/`skills` 视为同一术语（ humanize.ts 里
   `"添加 Skill "` 和 `" 到你的 Skills"` 就是同一术语的两种形态，都必须对上"技能"）。
4. 品牌词豁免：OpenWorker、GitHub 等专有名词不进术语表，保持英文原样不算不一致。

### 3.3 模板完整性：占位符中英文一一对应

**适用对象（按 §1 盘点修正）**：本仓库没有独立 prompt 模板文件，检查分两档——

- **现在就能查**：`humanize.ts` 的三段式文案模板。注意它的占位符不是花括号，
  而是 **obj 插槽**：`pre`/`post` 是中文片段，`obj` 是运行时填入的对象名。
  规则：pre/post 中文里不能混入未翻译的英文文案词（"到你的 Skills"里的 `Skills`
  应为"技能"，这条同时触发 3.2 术语检查）。
- **汉化后纳入**：`coworker/personas/builtin/ops.md` 这类 md prompt。
  规则见下。

**占位符识别规则**（以后端 md prompt 为准）：

| 风格 | 示例 | 说明 |
|---|---|---|
| 花括号 | `{input}`、`{output}` | Python/JS 通用 |
| printf | `%s`、`%(name)s` | C/Go 风格 |
| 双花括号 | `{{name}}` | 模板引擎风格 |

**规则**：

1. 中文文案中的占位符**集合**必须与英文原文的占位符集合完全一致：
   多一个、少一个都算失败（漏了 `{output}` 是最典型的翻车）。
2. 占位符**名称拼写**必须一致：`{input}` vs `{imput}`（少个字母）单独列为
   "拼写错误"，因为运行时直接报错，比漏翻更严重。
3. JSX 里的 `{variable}` 是 JS 表达式不是文案占位符，**不纳入**（如
   `label: "数字同事"` 外面的花括号是对象字面量）。
