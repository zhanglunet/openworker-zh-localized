## 3. 栏目信息架构

### 3.1 栏目名与定位

- **栏目名（评审点）**：推荐「**构建实录**」，英文对照 "Build in Public"；备选「Agent 造物实录」。栏目一句话：用 agent 一步步做出 OpenWorker 汉化版的过程，全部记在这里。
- 栏目定位句对齐主定位：「英文的 AI 桌面助手，中文的打开方式」→ 栏目版「一天天用 agent 造出来的中文版，过程也给你看」。
- 与 PRD-102 的关系：PRD-102 是**双语技术传播能力**（怎么写、中英怎么同步），本栏目是它的**传播形态与载体**（写什么、多久一篇）；栏目是 PRD-102 的第一个连载系列。

### 3.2 两层结构（文档层为单一事实源）

```
docs/articles/build-in-public/       # 文档层：单一事实源（T2/T3 落地）
├── README.md                        # 栏目索引：栏目名+定位句+篇目表+更新节奏+合规声明+借鉴声明
├── TEMPLATE.md                      # 首更模板（T2 交付，T1 只定骨架，见 §4.3）
└── 2026-11-<slug>.md                # 每篇一文件，文件名=发布日期+slug（kebab）

website/app/build-in-public/page.tsx # 站内层（T3 可选落地）：对标 /recommendation 的静态页形态
README.md / README.en.md             # 仓库层入口：目录区新增「构建实录」链接（T3）
```

| 层 | 职责 | 规则 |
|---|---|---|
| 文档层 `docs/articles/build-in-public/` | 正文唯一事实源；随仓库走 git，可引用 | 质量门自动覆盖（`docs/**`）；文章内不维护副本 |
| 站内层 `/build-in-public` | 中文站读者入口 | 页面从文档层**转写**，不双写正文；改稿先改 docs 再同步页面（对齐 recommendation 页现状做法） |
| 仓库层 README | 发现入口 | 只放栏目一句话 + 指向 docs 索引与站内页的链接 |

### 3.3 篇目元数据约定（每篇头部字段，T2 模板固化）

| 字段 | 约定 |
|---|---|
| `title` | 中文标题；动词开头优先（「造出了…」「修好了…」） |
| `date` | ISO 8601 日期（发布日） |
| `status` | `草案` / `已发布`；只有 `已发布` 才进索引表 |
| `tags` | 形态标签，枚举：`面板` / `打包` / `上游同步` / `文档` / `工具链`（新标签需在索引 README 登记） |
| `evidence` | 真实工作流事件背书：对应 PR 链接或 issue 链接（本仓库公开 PR/issue），≥1 条；**没有背书不发文** |
| `artifacts` | 可复现产物清单：仓库内相对路径或公开链接，≥1 条 |
| `bilingual` | 英文摘要段落锚点说明（T4 互通用，见 §5） |

### 3.4 栏目索引表（docs 索引 README 内，字段级）

| 列 | 说明 |
|---|---|
| 篇目 | 链接文章文件 |
| 一句话 | 40 字内摘要，写结论不写广告语 |
| 产物 | artifacts 第一条 |

## 4. 更新节奏与栏目运行规则

### 4.1 节奏

- **基线：至少月更一篇**；有合并事件（发版、新功能、面板/打包类里程碑）触发**事件加更**，不凑数、不补空文。
- 每篇绑定一次真实工作流事件（`evidence` 字段强制）：该篇讲的事必须能在仓库 git 历史/PR 里查到，实录不编故事——这是与 rakazo 形态对齐的核心（过程可查=可信=获客）。
- 首篇候选（T3 建议，评审点）：「中文上下文面板从设计到合并」——PRD-155 T1→T5 共 5 天 4 个 PR（2026-10-23 至 10-24 已合并，素材齐全：静态样机、演示数据契约、时间线），且有 issue/PR 可引用，完全满足 evidence 要求。

### 4.2 与周报的分工边界

| 维度 | `docs/updates/WEEKLY.md`（周报） | 本栏目（实录） |
|---|---|---|
| 生成方式 | git 历史自动转写，定时刷新 | 人工策划撰写，PR 评审后发布 |
| 粒度 | commit 级流水账 | 一次完整工作流事件（目标→过程→踩坑→产物） |
| 读者动作 | 查「发生了什么」 | 读「怎么做成、我能复用什么」 |
| 互链 | 实录文末链当期周报；周报不加回链（自动生成文件不改） | — |

### 4.3 篇章骨架（T2 模板的 T1 版约束）

四段强制，段名与 PRD-184 任务表一致：**目标 / 过程 / 踩坑 / 产物**。

- 「踩坑」为**必填段且不得为空话**：至少 1 条具体坑（现象→原因→解法）；写不出踩坑的选题不立项——这是 PRD 风险「写成广告腔 → 模板强制踩坑与数据」在骨架层的关闭。
- 「产物」必须给可复现路径（文件/命令/链接），虚拟样例标注 `<示例>`。

### 4.4 发布合规闸（对齐 PRD 风险「泄密 → 发布前扫描」）

每篇发布前逐项自查（T3 起作为 PR 描述 checklist 固化）：

1. **敏感信息扫描**：全文无密钥/token/账号/IP/内部主机名（占位符纪律，命中 `secret|password|credential|api[-_]?key|bearer|private[-_]?key` 与 IP 段正则的自查口径沿用 PRD-155/T1 §4.3 已验证的思路，人工执行，不新增 CI）。
2. **未发布安全细节**：不写未公开的安全修复、漏洞细节、签名材料办理进度等未发布事项（PRD 非目标）；引用 `docs/release-signing-deferred-plan.md` 只讲已公开结论。
3. **术语统一**：术语按 `scripts/quality-gate.py` 25 条拍板表；CI 对 `docs/articles/**` 自动跑（§2）。
4. **evidence 核对**：`evidence` 链接全部可公开访问且指向真实事件。
5. **数据诚实**：时间/token/次数等数字给区间或占位并标注，不夸大不虚构精确值。
